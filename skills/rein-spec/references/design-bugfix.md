# BUGFIX：design.md 输出规范

用于纠正已有行为偏差。交付有证据支撑、范围受控、能验证“不再出错且没有破坏正常行为”的修复设计。保留 Rein 的 `requirements.md` 和 AC ID 契约，不因参考 Kiro 而另建 `bugfix.md` 或改动状态协议。

## 输出原则

- 需求辨析、跨领域检索与最强反对者检查用于发现真实原因和排除错误修法。正文保留根因证据、选定修复和必要风险，不输出诊断流水账、逐条猜测过程或通用架构重设计。
- 区分用户报告、已复现事实和根因假设。根因未确定就说明证据缺口和下一项可证伪检查，继续澄清/调查，不把未经证实的假设包装成“设计已就绪”。不能声称尚未执行的回归测试已经通过。
- 在共享的出错位置修复，覆盖必要调用方，保留外部契约。大规模重构或新功能若确实不可避免，应先说明影响并与用户确认范围，不能以修 Bug 名义扩建系统。

## 建议文档结构

```markdown
# Bugfix Design: 缺陷名称

## Overview
简述缺陷、预期修复结果、影响范围和必须保留的行为，关联需求中的 AC ID。不重复所有调查记录。

## Bug Condition and Reproduction
### Trigger Condition
明确哪些输入、状态、操作顺序或时序触发缺陷；说明正确行为的依据和不受影响的输入域。
### Reproduction
提供最小步骤/输入、相关环境、期望与实际结果及已知证据。未能复现时标明用户报告和证据缺口，不能编造日志。

## Root Cause Analysis
将“触发条件 → 代码/数据/状态机制 → 错误结果”连成可核对的因果链，引用实际文件、函数、调用方或现有测试。只记录决定修复方向的关键证据；假设明确标注，不用症状描述代替原因。

## Fix Design
### Affected Components
列出需要改动的现有组件、函数和调用方，以及各自责任，不列无关系统模块。
### Proposed Change
具体说明在哪个共享位置改什么：触发后的 before/after 行为、关键判断或状态转换、必要的签名/数据契约。用小段接口或伪代码表达关键差异，不给整套产品重新选技术栈。
### Data and Interface Impact
仅在实际改变数据、配置、协议、持久化或公开接口时展开兼容和迁移；否则简短说明契约保持不变。

## Preservation and Boundaries
明确修复覆盖的输入域，以及域外哪些正常行为必须保持不变。说明边界、相邻路径、失败/取消/重试等相关行为为何不被破坏。范围内发现的新能力诉求单独澄清，不顺手实现。

## Validation Design
### Bug Reproduction
列出能够在修复前暴露缺陷的最小反例或现有失败用例，说明观察值和应失败的断言。
### Fix Verification
说明同一触发条件在修复后应得到什么结果，以及相关边界、时序或异常输入如何验证。
### Regression and Preservation
为必须保持的正常行为安排保留性验证，把“修复正确”和“原有行为不变”分别对应 AC ID 与测试位置。性质测试适合时再用，不为简单缺陷强加随机测试框架。

## Risks and Rollback
按改动风险记录残余证据缺口、并发/兼容风险，以及有必要的数据恢复或回退措施。小修复不编造发布平台或回滚系统。
```

## 交付前自检

- 修复是否针对有证据支持的原因？实现者能否从设计定位到具体改动和受影响调用方？
- 能否分别验证：旧行为暴露缺陷、修改后满足预期、正常行为继续成立？验证是计划还是已执行是否说清？
- 根因复杂时可加局部流程/时序图帮助解释；普通修复无需套用 FEATURE 的技术栈、全系统架构、数据库和部署章节。
- 红到绿的回归验证应在同一 Coding 任务完成，避免将必然失败的红测试单独交付而阻塞 Rein 顺序队列。

参考：[Kiro Bugfix Specs](https://kiro.dev/docs/specs/bugfix-specs/)、[Kiro 回归保护建议](https://kiro.dev/docs/specs/best-practices/)。本规范是适配 Rein 的修复设计格式，不复制 Kiro 的文件命名和测试工具要求。
