# FEATURE：design.md 输出规范

用于开发新功能、新产品或扩展已有系统。交付可供 Coding Agent 直接实现的技术设计，采用用户提供的 Kiro 示例那种“架构 → 组件 → 数据与接口 → 交互 → 验证”的组织方式。正文用用户的语言；以下标题可翻译，但保持结构清晰。

## 输出原则

- 先完成需求辨析、跨领域检索、约束整理和反证，再写最终选定方案。只保留影响技术决定的结论、必要依据与剩余风险，不把“思考过程”“跨领域搜索”“最强反对者”“方案反证”作为正文主线。
- 依实际规模展开。单页工具可以只有页面、控制器和纯逻辑模块；业务应用可以包含服务与持久化。示例的 React、Express、数据库、AI 服务、认证、Docker 或蓝绿发布不是默认配置，不能为凑目录而引入。
- 所有核心部分都必须有具体设计：模块名、职责、数据形状、接口约定、交互顺序和错误行为。不能只有原则口号、文件列表或“后续完善”。代码块用于关键类型、接口、schema、有限状态或核心伪代码，不写整套实现。
- 保留已确认的需求及 AC ID，不重新发明数值精度、容量、时限、安全等约束。需求未覆盖的关键决定先澄清；非阻塞假设明确标注。正确性不来自选用了某项技术，必须给出对应验证方法。

## 建议文档结构

```markdown
# Design: 功能名称

## Overview
用一小段说明实现目标、选定方案及系统边界，引用相关需求。列出真正影响实现的约束，不重复整份需求。

## Architecture Overview
### Technology Stack
说明实际技术选择、用途，以及沿用现有技术还是本次新增。仅对有取舍的选择补充简短理由。
### System Architecture
给出反映真实模块关系的架构图，标注运行位置、进程/网络/存储边界及依赖方向。模块可以位于同一进程，不能把每个函数画成独立服务。
### Key Decisions
仅记录影响架构的决定、关键依据和适用边界；无重要取舍时合并到技术选择中，不写候选方案淘汰过程长文。

## Component Design
### 组件或模块名称
职责、输入输出、依赖、状态归属，以及需要新增或修改的实际位置。前端说明组件关系和事件；后端或库说明服务边界、调用方和契约。

## Data Models
给出核心实体/状态的字段与类型、ID、可空性、状态转换和不变量。有持久化时给出相关表、约束、索引和关系；无持久化时描述内存模型，不虚构数据库。

## API Design
有 HTTP API 时说明方法、路径、请求/响应、校验、错误及相关权限；有事件时说明事件名、载荷和触发时机。纯前端/本地库改写为 Interface Design，给出函数、组件或模块接口，不编造 REST 服务。

## Data Flow
按关键用户操作描述“输入 → 校验 → 状态/存储变化 → 输出”，至少贯通一个主要流程与关键失败/恢复分支。需要时用序列图展示并发、异步和系统间交互；不要另画与实现无关的装饰图。

## UI/UX Design
涉及用户界面时说明布局、关键控件、操作反馈、加载/空/错误状态、必要的响应式和可访问行为。沿用已有设计系统；没有 UI 的项目省略本节。

## Error Handling
明确错误条件、传播或返回方式、对用户/调用方的表现、状态一致性及恢复方式。取消、重试、重复提交或部分成功仅在本功能涉及时展开。

## Security and Performance
仅说明与需求和架构相关的风险、约束及实现措施，不套用与本功能无关的 JWT、限流、缓存或分布式方案。范围较小时可并入相关组件设计。

## Testing Strategy
把 AC ID 映射到可验证行为、设计位置和验证方式，覆盖正常、关键边界、失败及恢复。适合通用不变量时给出性质测试；其他场景使用具体用例或集成验证。清楚区分已有验证证据与待执行测试。

## Deployment and Migration
按实际交付方式说明运行/构建入口、配置、数据/接口兼容及必要迁移。没有部署或迁移变化时只说明实际运行方式，不扩展出额外基础设施。
```

## 交付前自检

- 架构图、模块职责、接口名称、数据模型和流程是否互相一致？关键路径能否直接据此拆成实现任务？
- 每条 AC 是否有设计落点和验证方法？边界是否来自需求或已说明的必要决定？
- 读者是否能迅速找到“建什么模块、如何调用、数据如何变化、失败如何处理”，而不是先阅读长篇分析记录？
- 小功能删去无关可选节，但不能删掉核心架构、模块/接口、状态数据、流程和验证设计。不要用空模板、占位符或“同上”交付。
